# Long-term progress

## Contract

`ctx.longTermProgress.get(agent)` reads the registered `longTermProgress` Session projection and returns a detached state or `null` before the first list. `change(agent, { revision }, change, authority)` is the only durable mutation path. Revision zero creates the first list; each successful append increments the revision. Failed validation, stale revisions, disposed services, and non-live Agent handles reject without appending. Events carry the complete post-change state and validated operation; replay recomputes the transition and rejects mismatched settlements. A replay failure blocks host reads and mutations instead of authorizing work from stale state.

The structure has exactly two levels: milestones and checkpoints. IDs are stable branded strings, unique across the list. Checkpoints retain immutable evidence settlements, including across human-confirmed moves between milestones. An evidenced outcome requires a new checkpoint ID when its condition changes. Completion requires the latest settlement to contain a passing observation and at least one reference. A failed observation reopens a current checkpoint without removing prior evidence. Accepted milestones cannot be rewritten; a demonstrated historical failure inserts a repair checkpoint into the current milestone at an explicit position. The caller owns the dependency analysis and must ask a human when the safe position is ambiguous.

Human adapters must derive `ProgressAuthority` from their live command, UI action, or direct-human tool interaction. It is a trusted same-process parameter, not a wire/model argument. Replacement, approval, release (`start`), acceptance, document references, and vault linking require human authority. Approval does not release. Release records scope permission only: no method starts, resumes, queues, injects, or arms execution. Acceptance requires nonempty evidence-complete checkpoints and earlier approval, clears release and Goal binding, and never releases the next milestone. Structural replacement revokes unaccepted milestone approvals, release, and Goal binding; accepted milestones retain their historical approval evidence. Refinement requires a concrete `reason` persisted with the operation and can change only implementation detail and references, never the checkable outcome.

`eligibleCheckpoints` in the source domain module checks a nonempty consecutive unfinished prefix in the current released milestone. Goal adapters must combine that scope check with their process-local activation, cancellation, and direct-human policies. A Goal phase cannot settle progress. The `bind-goal` operation records an eligible association but does not create a Goal.

## Commands and tools

`/long-goal` or `/long-goal status` shows compact state. `/long-goal draft <revision> <milestones JSON>` replaces the draft using stable milestone/checkpoint IDs. `/long-goal approve <id> <revision>`, `/long-goal start <id> <revision>`, and `/long-goal accept <id> <revision>` are distinct human decisions; the explicit revision prevents stale commands from granting permission to changed scope. None schedules execution. Malformed input and stale revisions leave progress unchanged.

`read_progress` returns all milestone captions, counts, status and the revision by default. Optional `milestone_id` or `checkpoint_id` retrieves only the selected details and references; a combined selector must identify a checkpoint in that milestone. `update_progress` accepts an exact `revision` and strict `change` union. Evidence reconciliation and implementation-only refinement are autonomous; structural changes and human decisions always use the existing in-flight question service, including during direct-human turns. Confirmation shows the complete proposed operation, requires the explicit Confirm choice, and rechecks the revision and live caller after the answer. Missing interaction support, cancellation, disposal or stale confirmation rejects without mutation. Authority is never accepted from model JSON. Internal Goal/vault settlement operations are unavailable through this tool.

The command registers only when the command service is composed; model tools register only when the tool service is composed. Removing the progress fiber removes both registrations and aborts pending confirmations. The durable service remains usable without either consumer.

## Scoped execution Goals

When the Goal service is composed, `advance_progress_goal` accepts the exact progress revision, a released milestone, consecutive unfinished checkpoint IDs and an objective. It creates or edits the existing execution Goal; several Goals may cover partial work on one checkpoint, and a Goal may cover several consecutive checkpoints. Ordinary unbound create/edit operations reject with a clarification request instead of guessing objective similarity. Existing Goal tools keep their direct-human restrictions. Pause, cancellation, restart, fork and plugin reload cannot regain automatic execution from durable approval alone; a fresh human start or permitted explicit resume restores the process-local release. Unloading the progress adapter disarms Goals it authorized.

A Goal switch makes lightweight reconciliation pending. The next logged reminder instructs the Agent to use recent observations and targeted checks; implementation tools and another Goal switch wait for `reconcile`, or `review` with a concrete reason when there is no new evidence. Review records no completion. Passive evidence may settle later unaccepted checkpoints without releasing them. Completed checkpoint groups cannot receive more automatic work; the next eligible group may advance within the same fresh release. The final checkpoint disarms continuation for human verification, and acceptance never releases the next milestone. A failed Goal binding append leaves the execution Goal disarmed and reports the failure rather than claiming both operations committed atomically.

## Optional existing checklist synchronization

`link_progress_checklist` confirms one existing regular file, its opaque provider identity, a fingerprint and explicit checkpoint-to-marker mappings. Entries use stable `<!-- dsh:marker -->` comments, not captions or line numbers. Checkbox updates have standing permission after confirmation; implementation-text synchronization requires the independent `allow_text_refinement` choice. No project or checklist is created. Association rechecks both file contents and Session revision after the answer. Forked associations retain references but suspend writeback until linked again.

Evidence or detail changes mark the association pending in the same Session transition. The next turn inspects the file; progress tools also attempt synchronization after their result. `sync_progress_checklist` explicitly retries. All reads and guarded atomic writes use the composed filesystem service, its current Session sandbox policy and provider version token. The complete file is limited by `maxChecklistBytes` (1048576 by default). Exact bytes outside mapped lines, manual notes and line endings are preserved. Missing/duplicate markers or a changed target identity report a conflict. External file changes ask separately for each mapped checkpoint, showing both values; Keep checklist can import a human-verified checkbox observation or approved implementation detail, but a changed outcome requires a structural draft. A newer edit invalidates an answered confirmation.

Session commits and file writes are separate operations. Pending, failed and conflicting settlements remain visible; a write refusal never removes checkpoint evidence or blocks unrelated authorized execution. An interrupted settlement reports that both stores need review rather than asserting synchronization. A retry with already matching contents performs no write. Plugin disposal aborts and drains owned synchronization/association operations; late answers cannot publish another file or Session change.

## Configuration

All bounds are positive safe integers: `maxMilestones` defaults to 64; `maxCheckpoints` to 256 per milestone; `maxTextLength` to 4096 UTF-16 code units per content field; `maxReferences` to 64 per collection; `maxHistory` to 1024 per other retained collection. Content includes captions, outcomes, implementation details, reasons, evidence summaries, references, and vault text, not fixed protocol literals or stable IDs. IDs retain their separate 128-code-unit protocol bound. Admission checks the complete incoming operation and next state, rejecting oversized lists rather than dropping captions. Prior state and replay validate durable invariants independently of deployment limits, so an existing oversized list can be replaced with content within reduced limits; operations that leave an oversized result still reject.

## Persistence and lifecycle

`progress/change` version 1 is a required-on-read Session event. The service registers its pure projection through the existing Session projection registry with `stateVersion: 5`. Its cache schema validates unique identities, evidence/completion and committed-revision consistency, approval/release/acceptance relationships, released Goal scope, and agreement between inherited replay and suspended child state. Invalid cache rows cannot supply authority: `hydrate`/`restore` reject them, while checkpoint-only reads omit the key. The restoring owner must report the failure and explicitly rebuild from the Session log rather than accepting or repairing cache-granted release. Forks retain inherited progress and references, suspend child vault writeback, and clear inherited Goal bindings without modifying the parent. Renewed human `vault-link` confirmation is required before child settlements. Reload restores durable scope decisions but cannot activate execution because this package has no execution integration. All registrations are owned by the plugin fiber; retained handles reject mutation after disposal.

The wire value is `ProgressProjectionView`: `{ status: 'ready', current }` before and after list creation, or `{ status: 'untrusted', current, failure }` after replay corruption. In an untrusted value, `current` is last-good display data only. The persistent failure supplies `code: 'PROGRESS_REPLAY_FAILED'`, `eventSeq`, and a diagnostic `message`; snapshots, change-feed notifications, and cached reads retain it. Host reads and mutations throw `ProgressError` with that code. Consumers must stop dependent work, localize an actionable corruption report, and have the restoring owner inspect the Session log before rebuilding; later events do not clear the failure or make last-good scope authoritative.

Vault metadata settlements are not filesystem writes. The adapter must validate current contents, compare the approved fingerprint immediately before writing, preserve stable marker mappings and unrelated content, and report pending, failed, or conflicting synchronization instead of claiming atomic Session/filesystem success. Checkbox permission does not grant text-refinement permission.

## Model Experience

The first admitted request of each turn receives one logged milestone-caption snapshot; requests following tool results reuse that history without another snapshot. The reminder includes every milestone identity, title, caption, completion count and authorization/verification status, but no checkpoint bodies, evidence or document contents. It states that the latest revision supersedes earlier snapshots and that bookkeeping does not authorize execution. A newly emptied list contributes a clearing snapshot; a Session that never had progress contributes nothing. Rejected, cancelled or empty admission adds no reminder and does not suppress a later admitted retry. Snapshots append to request history and therefore consume tokens and extend the KV cache once per turn; selective reads add only requested details. Saving progress never generates an execution plan or execution authority.

## Known Limitations and Deferred Work

The UI consumer and shipped composition are separate integrations. They must not pass model-supplied authority or silently execute saved scope. Product composition, both SDK acknowledgements, Session compatibility acknowledgements and catalog regeneration, recorded-session snapshots, package classification, and final integration validation are owned by the integration task. The package does not provide a scheduler, evaluator, workspace database, or global progress page.
